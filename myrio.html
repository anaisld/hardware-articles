Developing a Smart Industrial Mixer with NI myRIO and LabVIEW

An embedded-control prototype combining program-dependent motor speeds, rotary encoder feedback and an I²C LCD interface.

In this laboratory, we developed the control interface for a professional food mixer using NI myRIO and LabVIEW. The target system had to select a mixing program, command a DC motor, display its operating state and measure rotational speed. The specification also included vibration detection and closed-loop speed regulation, which were not fully implemented during the session.

Engineering objective

Connect the user interface, motor drive and sensors in one continuously running virtual instrument (VI), while allowing operators to change programs without restarting LabVIEW.

Software architecture: a continuously running virtual instrument

The LabVIEW VI was structured around a main while loop that keeps the interface responsive, with a Case Structure activated by the start button. Program selection, direction indication and speed measurement were grouped within this logic. This approach allowed the selected recipe to change during execution rather than requiring the VI to be relaunched.

LCD interface over I²C

The display was initialized once using an I²C Express VI, before the recurring control loop. The first LCD row was designed to show the current time in 24-hour format and the day/month date. LabVIEW date/time functions extracted the relevant fields, converted them to strings and concatenated them into the expected display format.

The second row was intended to show the selected program when the machine was not vibrating, or a vibration warning with the affected axis when the accelerometer detected movement. The team implemented the program display but did not complete the accelerometer-based alert.

The report also records a display-reset limitation: after stopping and restarting the VI, the LCD could retain an outdated program label even though the LabVIEW front panel updated correctly.

Mapping mixing programs to motor commands

Four operating programs—Pâte, Crème, Farce and Œuf—were selected through a numeric Case Structure. Each branch updated the program name and number, and associated the chosen program with a speed derived from the specified maximum of 5 revolutions per second.

The selected speed was normalized for the PWM output, which expects a duty-cycle value between zero and one.

PWM command used in the prototype
D = vset / vmax

With vmax = 5 rev/s, the programmed duty cycle is obtained by dividing the selected speed by five. This is an open-loop mapping between requested speed and PWM duty cycle; it does not guarantee that the motor reaches the requested speed under load.

Indicating the rotation mode

A Boolean Case Structure selected the operating direction label: Malaxeur (mixing) or Débourreur (unblocking). The selected state was displayed on the VI front panel along with the current program.

The report demonstrates the direction-selection logic and display indication; it does not establish that a motor-driver polarity reversal was validated experimentally.

Measuring rotational speed with an encoder

Motor speed feedback was acquired using the Encoder Express VI. A shift register retained the previous counter value so that successive readings could be subtracted. The motor specification cited 12 encoder pulses per motor revolution and a 19.225:1 reduction ratio.

Encoder-based output-shaft speed
vout = (ΔN / Δt) / (12 × 19.225)

Here, ΔN is the difference between successive encoder counts and Δt is the measurement interval in seconds. The report's implementation additionally multiplied its computed value by 100 to obtain the expected display scale. Because the report does not explicitly document the measurement interval, that factor cannot be independently verified as a time-base conversion.

The measured speed was routed to a numeric indicator, a graph and a gauge, allowing the user to compare the motor's behavior across operating programs.

Observed results and remaining control challenges

The report includes front-panel results for the Farce and Crème programs, including a Crème example at the specified maximum speed and a Farce example at vmax/2.5.

Low PWM commands were insufficient to start the motor reliably in some programs. The team identified the need for a speed-feedback controller to compensate for the motor's startup threshold and load-dependent behavior, but did not implement the PID regulator before the end of the laboratory.

Proposed next step: closed-loop speed control
e(t) = vset(t) − vmeasured(t)

A controller could use the measured speed error to adjust PWM duty cycle. This is a proposed improvement, not a completed or validated result of the laboratory work.

The report contains a minor inconsistency in its description of which two programs operated successfully. Rather than assigning unverified performance to a particular mode, the article uses the two front-panel examples documented in the report.

Engineering takeaway

This prototype demonstrates the integration of LabVIEW control logic, I²C communication, PWM motor actuation and encoder feedback into one interactive mechatronic interface. It also illustrates an important distinction: displaying a speed setpoint and measuring actual speed does not constitute closed-loop regulation until the measurement is used to correct the motor command.

Project outcome

The core VI, program selection, LCD program display, PWM speed command and encoder-based speed readout were developed. Accelerometer alerts, LCD reset handling and PID speed regulation remained to be completed.
